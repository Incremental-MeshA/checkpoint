# Инкрементальное планирование на car16

## Эксперимент с деревом префиксов MPGAA*

Ключ `--prefix-experiment` запускает пять вариантов. Контроли — исходный MPGAA* на lattice и mesh. На mesh добавлены `mpgaa_local` (при понижении оценки внутреннего узла сразу переходит к его единственному предшественнику), `mpgaa_chain` (сворачивает неветвящиеся цепочки) и `mpgaa_local_chain` (оба изменения). Для свёрнутого ребра хранятся полный след и исходное число шагов. Отбор изменённых рёбер, проверка сохранённой политики и поиск используют этот след. В журналах локальных вариантов `local_repair_steps` считает переходы к внутреннему предку в обход очереди ремонта.

Пример воспроизведения полного эксперимента в PowerShell после сборки Release:

```powershell
foreach ($p in '0.1','0.5','1','5','10') {
    python -m bench run --prefix-experiment --profile long --episode-seconds 60 --change-percent $p --output "runs/prefix-repeat/navigation-$p"
}
foreach ($r in 25,50,100,200) {
    python -m bench run --prefix-experiment --profile long --episode-seconds 60 --config config/visibility.json --radius $r --output "runs/prefix-repeat/visibility-$r"
}
python -m bench.prefix_report runs/prefix-repeat results/prefix-repeat
```

Для повторения с зафиксированной Windows-сборкой укажите путь к ней в `MESH_PLANNER`. Для генерации HTML нужен Matplotlib. В сводке каждая настройка сравнивается на общей выборке пяти вариантов. [Отчёт](results/prefix/timing.html) · [Средние и счётчики](results/prefix/means.csv) · [Исходы](results/prefix/outcomes.csv)

Стенд сравнивает A*, D* Lite и MPGAA* на двух представлениях одного пространства движений. Каждый алгоритм ведёт своего робота к фиксированной целевой позе. Доступны сценарии с полностью известными изменениями и с ограниченной видимостью. В комплект входят 12 карт Moving AI с исходными задачами, авторские примитивы и измерения быстрых серий.

## Запуск

Нужны компилятор C++17, CMake ≥ 3.16 и Python 3.9 или новее. Python-код использует стандартную библиотеку. Команды выполняются из корня проекта.

```shell
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
python -m bench prepare
python -m unittest discover -s tests -v
python -m bench run --profile quick --change-percent 0.1 --budget-seconds 300
```

Доли изменений для сравнения заданы в `config/benchmark.json` в списке `change_percents` (0,1%, 0,5%, 1%, 5%, 10%). Одну серию выбирает параметр `--change-percent`, например `--change-percent 0.5`. Готовая сборка Windows лежит в `build`. В PowerShell интерпретатор на машине для замеров можно вызвать по полному пути.

```powershell
$python = Join-Path $env:LOCALAPPDATA 'Programs\Python\Python314\python.exe'
& $python -m bench run --profile quick --change-percent 1
```

Команда печатает путь к новому каталогу в `runs/`. Путь можно задать через `--output`. Для запуска со своей сборкой задайте переменную окружения `MESH_PLANNER` с путём к исполняемому файлу.

```shell
python -m bench compare results/quick-10
python -m bench replay results/quick-10/random512-10-0-L119-astar-mesh-r0.jsonl
python -m bench replay results/quick-1 --regenerate
python -m bench run --profile long --change-percent 1 --budget-seconds 3600 --repeats 2
```

`compare` выводит CSV по полностью измеренным комбинациям задачи и повтора. `replay` принимает журнал эпизода или каталог серии, применяет сохранённые правки и сверяет запросы, маршруты, исходы и счётчики. С `--regenerate` правки заново генерируются из seed. Из сравнения исключены только поля времени.

## Интерактивная карта

Включите «Animate edge checks» перед запуском, чтобы просмотреть перебор соседей. На lattice и mesh видна полная траектория примитива. Для общего префикса mesh тонкие линии показывают все возможные продолжения от исходной позы. Проверяемое ребро выделено поверх траекторий, красный пунктир обозначает заблокированное ребро. Кнопки перехода по кадрам позволяют рассмотреть кандидатов по одному.

Под каждой картой видны два счётчика за текущий запрос. «Cell checks» учитывает каждое чтение занятости клетки планировщиком, включая повторные проверки. Число уникальных проверенных клеток видно при наведении на строку показателей. «State expansions» учитывает каждое раскрытие вершины графа при поиске и восстановлении эвристики. Для mesh сюда входят промежуточные состояния манёвров.

Переключатель «Side by side» открывает два планировщика с общей картой, задачей, сценарием и seed. Выберите алгоритм и граф для каждой стороны и нажмите «Run». Камеры и перемотка связаны. На каждом ходу можно просмотреть поиск с обеих сторон до следующего перемещения. Если один робот закончил раньше, его итог остаётся на экране до конца второго эпизода.

После сборки выполните `python -m bench visualize`. Откроется локальное меню на английском языке. Выберите карту, готовую задачу или пункт «Choose on map», сценарий, алгоритм и граф. В ручном режиме укажите свободные клетки старта и цели и задайте их направления. Кнопка «Run» запускает один эпизод. Seed в меню задаёт непосредственно генератор эпизода. Чтобы повторить условия журнала, скопируйте seed из его первой строки.

Колесо мыши меняет масштаб, перетаскивание перемещает карту. При приближении нажмите на позу вдоль текущего плана, чтобы увидеть допустимые манёвры и выбранную траекторию. Ползунок и кнопки под картой управляют воспроизведением. В сценарии ограниченной видимости переключатель «Show actual map» показывает изменения за пределами наблюдения. Трассировка включается только в интерактивном режиме.

Для запуска без автоматического открытия вкладки используйте `python -m bench visualize --no-browser`. Сервер напечатает адрес и будет работать до Ctrl+C.

## Навигация с ограниченной видимостью

Конфигурация `config/visibility.json` запускает все шесть планировщиков на восьми новых картах. Каждый радиус измеряется отдельной серией. В PowerShell из корня проекта:

```powershell
$python = Join-Path $env:LOCALAPPDATA 'Programs\Python\Python314\python.exe'
foreach ($r in (Get-Content -Raw config/visibility.json | ConvertFrom-Json).radii) {
    & $python -m bench run --config config/visibility.json --radius $r
}
```

Старт и цель берутся из исходных `.scen`. Используются городские карты `Berlin_2_512`, `Boston_2_512`, `Milan_0_512`, `Moscow_1_512` и лабиринты `maze512-4-0`, `maze512-8-0`, `maze512-16-0`, `maze512-32-0`. Все имеют размер 512×512. Городские карты предоставлены Konstantin Yakovlev и Anton Andreychuk, лабиринты — Nathan Sturtevant / HOG2. Скачанные файлы и их SHA-256 перечислены в `config/sources.json`. [Городские карты Moving AI](https://www.movingai.com/benchmarks/street/index.html) · [Лабиринты Moving AI](https://www.movingai.com/benchmarks/maze/index.html)

- Агент начинает с копии исходной карты. В фактическом мире перед первым наблюдением блокируются 5% исходно свободных клеток. Через каждые 20 полностью исполненных примитивов блокируются 0,5% клеток, свободных перед событием, и одновременно освобождается столько же клеток из всех занятых перед событием. Обе выборки равномерны, размеры округляются до ближайшего целого с половиной вверх. Клетки робота и цели защищены.
- На старте и после каждого примитива агент наблюдает клетки внутри евклидова круга радиусом 25, 50, 100 или 200 клеток, включая границу. Стены внутри круга не закрывают обзор. За пределами круга агент хранит последнее известное состояние каждой клетки. На шаге 20 изменение мира предшествует наблюдению. При достижении цели эпизод завершается сразу.
- Первое наблюдение передаётся вместе с первым запросом. Затем новая видимая блокировка или разблокировка вызывает перепланирование из текущей позы. При отсутствии новых сведений робот продолжает уже найденный маршрут. Весь след исполняемого примитива проверяется на фактической карте. Исход `no_path` означает отсутствие пути **на известной агенту карте**.
- Seed мира одинаков для всех планировщиков и радиусов при той же задаче и повторе. В JSONL запись `world` содержит фактические правки, а `request` — только обнаруженные изменения относительно карты планировщика. В CSV `events` считает перепланирования, `world_updates` — периодические изменения мира после старта. В обычном replay наблюдения заново вычисляются по сохранённым изменениям мира. С флагом `--regenerate` заново генерируется и сам мир.

Профиль `quick` использует восемь зафиксированных пар, по одной на новую карту, всего 48 эпизодов на радиус. В `long` доступны все 24 подготовленные пары новых карт. Для измерения того же набора пар при другом сценарии можно скопировать конфигурацию и изменить `scenario` и `change_percent`. Набор задач быстрого профиля задаётся в `profiles.quick.pairs`.

## Профили и данные

Для исходной конфигурации `config/benchmark.json` на четырёх случайных картах используются следующие объёмы.

| Профиль | Пар на карту | Карт | Повторы по умолчанию | Эпизодов на одну долю |
|---|---:|---:|---:|---:|
| quick | 2 | 4 | 1 | 48 |
| long | 3 | 4 | 3 | 216 |

Файл `config/benchmark.json` задаёт карты, список идентификаторов пар, сценарий, seed изменений, число повторов и бюджет. Пустой список пар выбирает все пары профиля. Свою копию можно передать через `--config`. Бюджет действует на последовательную серию всех шести вариантов. `timeout` обозначает прерванный эпизод, `not_run` — эпизод, до которого очередь не дошла. Уже записанные запросы и результаты остаются в журнале.

В `config/tasks.json` зафиксированы строки исходных `.scen` с нумерацией от единицы, координаты, направления, seed выбора поз, начальная оптимальная стоимость и длина в примитивах. На этапе отбора используются интервалы длины сеточного пути [42, 62), [65, 87), [90, 115) клеток. Внутри интервала кандидаты упорядочены по хешу, направления задаются до проверки достижимости. Берётся первая пара, для которой lattice A* нашёл путь длиннее десяти примитивов. Для среднего и длинного интервалов на новых картах порог составляет двадцать примитивов. Быстрый профиль использует два интервала на каждой карте. Назначение интервалов чередуется между картами. `python -m bench prepare --select` воспроизводит полный отбор.

`prepare` проверяет SHA-256 по `config/sources.json` и загружает отсутствующие файлы. При полном каталоге `data/` подготовка, прогоны и повторное воспроизведение работают офлайн. Координаты задаются как `(x, y, heading)`, начало координат в левом верхнем углу. Номер направления совпадает с номером в наборе управлений.

Sturtevant, *Benchmarks for Grid-Based Pathfinding*, IEEE TCIAIG, 2012. [Карты и сценарии](https://www.movingai.com/benchmarks/random/index.html) · [Условия распространения](https://www.movingai.com/benchmarks/grids.html)
- 384 примитива взяты из набора `base_control_set.txt`, ревизия `12574ff03d8d61ac153b4e4224eac2229a9577e1`. Исходная MIT-лицензия включена в `data/MeshAStar-LICENSE.txt`. [Набор MeshAStar](https://github.com/PathPlanning/MeshAStar/tree/12574ff03d8d61ac153b4e4224eac2229a9577e1/data)

## Сценарий с полной видимостью изменений

Для карты 512×512 при долях 0,1%, 0,5%, 1%, 5% и 10% за событие меняются соответственно 131, 655, 1 311, 6 554 и 13 107 клеток **в каждую сторону**. Выбор идёт без повторений по состоянию карты до события. Цель и текущая клетка робота остаются свободными. При достижении точной целевой позы эпизод заканчивается, в том числе на десятом шаге. Если после изменения пути нет, результатом становится `no_path`.

Для общей задачи и повтора у всех вариантов одинаковый порядок кандидатов. При равной оптимальной длине допустимы разные маршруты. Поэтому запросы после десятого шага, защищённая клетка и даже исход эпизода могут различаться. Количество достигнутых целей следует читать вместе с временами. Для проверки стоимости на идентичных запросах в тестах используется независимая Дейкстра.

## Реализация

- В `algorithms/` находятся три реализации. Поисковый код получает ориентированный граф через общий интерфейс. В lattice переход соответствует целому примитиву. В mesh одинаковые префиксы следов для одного начального направления объединяются. Промежуточные рёбра имеют нулевую длину, завершение возвращает исходный ID примитива и начисляет его длину. Координаты препятствий проверяются по полному следу. [Конструкция MeshA*](https://ojs.aaai.org/index.php/AAAI/article/download/41004/44965)
- Первый компонент стоимости сохраняет точную сумму прочитанных binary64-длин, второй считает рёбра данного графа. Такая развязка делает продвижение по нулевому префиксу строго положительным в лексикографическом порядке. Для вывода в JSON сумма переводится в binary64. Эвристика использует масштабированное евклидово расстояние. На mesh прямой поиск учитывает возможные завершения, обратный — начало префикса. Все варианты проверяют, существует ли хотя бы один допустимый манёвр из старта и в цель.
- A* начинает поиск заново. D* Lite сохраняет для каждой вершины лучший переход вместе с `rhs`. При открытии ребра достаточно сравнить его стоимость через соседа с текущим минимумом. При потере лучшего перехода алгоритм заново выбирает его среди доступных соседей. Из этих переходов собирается маршрут. При равной стоимости выбирается первое ребро в исходном порядке графа. [D* Lite](https://idm-lab.org/bib/abstracts/Koen02e.html)
- MPGAA* индексирует вершины с выученной эвристикой. Открытое ребро `u → v` запускает восстановление при `h(u) > cost(u,v) + h(v)`. При повторном использовании пути планировщик проверяет каждое сохранённое ребро напрямую. Если хвост пути непригоден, результат проверки запоминается до конца запроса. [MPGAA*](https://www.cs.toronto.edu/~jabaier/publications/HernandezAB15.pdf)
- Сценарий находится в `bench/navigation.py`. Следующий сценарий можно зарегистрировать в `SCENARIOS` в `bench/__main__.py`. Один нативный процесс обслуживает все запросы эпизода, поэтому его поисковое состояние сохраняется между событиями.

## Измерения

| Поле | Смысл |
|---|---|
| `batch_seeds` | Уникальные вершины, с которых начинается обработка пакета. Для D* Lite это вершины, где закрыт лучший переход или открыто более предпочтительное ребро. Для MPGAA* это вершины с первоначальным понижением `h`. У A* значение равно нулю. |
| `plan_ms` | Время запроса внутри C++, включая применение пакета правок, обновление инкрементального состояния, поиск, восстановление примитивов и проверку маршрута |
| `apply_ms`, `changed_edges_ms` | Применение пакета к карте и отбор изменённых рёбер с группировкой исходных вершин для обновления |
| `search_ms`, `path_ms` | Остальная работа планировщика (включая распространение изменений, проверку сохранённого пути и учёт раскрытий) и финальная сборка, декодирование и проверка возвращаемого маршрута. Сумма четырёх времён равна `plan_ms` |
| `first_ms`, `replan_ms` | Время первого запроса и сумма времён следующих запросов |
| `total_ms` | Инициализация графа и планировщика, все запросы, генерация изменений и симуляция движения. Файловый и межпроцессный ввод-вывод исключены |
| `expanded`, `expanded_cells` | Общее число раскрытий, включая повторные, и число уникальных координат за запрос. Для MPGAA* сюда входят раскрытия из очереди восстановления |
| `search_expanded`, `repair_expanded` | Раздельные раскрытия из OPEN и вспомогательной очереди. Проверки рёбер при вычислении одношаговой оценки учитываются временем обновления |
| `open`, `repair_queue` | Счётчики вставок, извлечений минимума, изменений ключа, явных удалений и чтений минимума. Извлечение учитывается одной операцией |
| `expanded_cells_sum` | Сумма значений `expanded_cells` по запросам эпизода. Одна клетка может учитываться в нескольких запросах |

`run.json` содержит состав серии, платформу, версию компилятора, параметры сборки, хеш исполняемого файла и SHA-256 входных данных. `wall_seconds` измеряет фактическое время серии с запуском процессов и журналированием. В `summary.csv` одна строка соответствует эпизоду. JSONL содержит позу и число исполненных примитивов перед запросом, оба списка правок, полный новый маршрут, стоимость и счётчики. В списках правок клетка кодируется как `y * width + x`.
